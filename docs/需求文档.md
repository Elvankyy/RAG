## 2. 背景与目标

### 2.1 背景

需要建设一个企业级知识库管理平台，把分散的 PDF、Markdown、Word、TXT 文档导入为可检索的知识单元，并提供：

- 组织架构、角色与菜单/按钮级权限；
- 全局 / 部门 / 角色 / 个人四维混合数据权限；
- 登录态下的 AI 鉴权检索问答，未授权内容明确提示但不泄露；
- Agent 访问、Token、响应时间、知识热度等运营看板；
- 高频问题挖掘、FAQ 审核发布与缓存加速、知识缺口识别。

### 2.2 目标

1. 知识管理员可通过界面完成单篇/批量/目录导入，文档自动解析、切片、向量化并可检索。
2. 知识单元支持增删改查、版本管理、启停用与四维数据权限配置。
3. 普通用户登录后通过 AI 工作台提问，只能获得有权限的内容；无权限召回项给出明确但脱敏的提示。
4. 管理员可查看看板、审核 FAQ、处理知识缺口，形成“问答 → 沉淀 → 补全”的闭环。
5. 本地 Docker Compose 可一键启动，断网时可通过 mock provider 完成演示。

### 2.3 设计原则

- **权限是硬边界**：任何对外响应与 Prompt 都只包含授权内容；权限判断以 PostgreSQL 为事实源。
- **先鉴权后生成**：检索到的候选先做权限判定，再决定上下文与提示。
- **关系数据与向量数据分离**：PostgreSQL 负责事务与权限，Milvus 负责召回，MongoDB 负责会话消息，MinIO 负责文件。
- **异步任务可重试**：导入、嵌入、FAQ 挖掘、看板聚合全部走 Celery，不使用进程内队列。
- **可离线演示**：远程模型网关不可用时，切换到 mock provider 仍可跑通全链路。
- **可回滚**：知识单元保留版本快照，编辑即生成新版本，可回滚历史版本。

- FAQ 缓存命中仍需校验 ACL；未授权提示默认只给数量。
- 知识单元编辑即发布，不引入审批流；附件与目录导入纳入 v1。

## 5. 总体架构

### 5.1 逻辑架构

```
浏览器 (Vue 3 + Element Plus)
   │ HTTPS / SSE
   ▼
Nginx ──► FastAPI（统一 /api 前缀）
             ├─ API 层：参数校验、鉴权、SSE
             ├─ Service 层：用例、事务、权限裁决
             ├─ RAG 层：解析、切片、嵌入、召回、重排、Prompt、缓存
             └─ Repository 层：PG / Milvus / Mongo / MinIO / Redis
   ┌────────────┼──────────────┬───────────────┐
   ▼            ▼              ▼               ▼
PostgreSQL    Milvus         MongoDB          MinIO
(事实源)      (向量+切片)    (聊天消息)       (原始文件)
   │
   └── Celery worker / beat ── Redis（broker + 缓存 + 进度）
```

分层规则：

- `api` 只做参数校验、鉴权依赖、响应封装，不写业务。
- `service` 编排事务与权限，不直接拼 Milvus/Mongo 查询。
- `rag` 只处理检索/生成领域逻辑，通过 repository 访问存储。
- `repository` 封装外部存储，便于替换与测试。
- 跨模块契约集中定义在 `core/contracts.py`（状态枚举、SSE 事件、权限码）。

| 服务 | 镜像/构建 | 端口 | 持久化 | 用途 |
|---|---|---|---|---|
| `postgres` | postgres:16-alpine | 5432 | `pgdata` | 事实源 |

| `etcd` | quay.io/coreos/etcd:v3.5.18 | 2379 | `etcddata` | Milvus 元数据 |
| `milvus` | milvusdb/milvus:v2.5.27（实施时锁定已验证版本） | 19530/9091 | `milvusdata` | 向量库 |
| `backend` | backend/Dockerfile | 8000 | — | FastAPI |
| `worker` | 同上，Celery worker | — | — | 导入/嵌入/挖掘 |

Nginx 要点：SSE 关闭缓冲（`proxy_buffering off`、`X-Accel-Buffering: no`），读超时 300s；`client_max_body_size` 与上传限制一致。

### 5.3 技术默认约定

- 密码 Argon2id（或 bcrypt cost ≥ 12）；Access JWT 2h、Refresh 7d；`users.token_version` 吊销；权限请求级从 DB/Redis（TTL 300s）读取。
- 业务主键 BIGINT 自增；`unit_code` 人类可读；Milvus `unit_id/chunk_id` 用 INT64 映射。
- DB 存 UTC，聚合/展示按 `Asia/Shanghai`。
- 用户/单元/FAQ/会话软删除；敏感操作写 `audit_logs`；Milvus/MinIO 异步清理。
- 统一 `/api` 前缀；分页 `page/page_size`（默认 20，最大 100）；错误结构 `{code, message, detail, request_id}`。
- 单文件 50MB、单批 50 个、PDF 200 页；扩展名 + 魔数校验。
- Milvus 查询用 `Strong`/`Session` 一致性；启动探针检查 BM25/中文 analyzer/ARRAY 能力。
- Compose 最低 8GB RAM、4 核、20GB 磁盘。
- 首 token P95 < 2s；检索+权限+rerank P95 < 1.5s（不含网关排队）。

#### 6.1.3 关键索引与约束

- `users(username)` 唯一；软删除用户禁止硬删。
- `user_roles(user_id, role_id)`、`role_permissions(role_id, permission_code)` 唯一。
- `knowledge_units(unit_code)` 唯一；`(category)`、`(status)`、`(updated_at)`、`(checksum)` 索引；标题/正文可加 `pg_trgm`（中文可选 `zhparser`）。
- `unit_versions(unit_id, version)` 唯一。
- `unit_permissions(unit_id, target_type, target_id)` 使用 `UNIQUE NULLS NOT DISTINCT`（PG 15+），或 global 固定 `target_id=0` + CHECK；`target_type` 加 CHECK 枚举；`(target_token, unit_id)` 索引。
- `faqs.related_unit_id`、`knowledge_gaps.resolved_unit_id` 在单元删除时 `SET NULL`。
- `faq_units(faq_id, unit_id)` 唯一；FAQ 的 ACL 由该表全部关联单元的 ACL 取交集。
- 部门树禁止成环；删除部门前校验无子部门与成员；删除角色前校验未分配给用户；用户删除采用软删除。
- `unit_code` 采用 `KU-YYYYMMDD-####`，由 PG 序列生成，避免并发冲突。
- 日志保留：`qa_access_logs` 默认 180 天（`QA_LOG_RETENTION_DAYS`），Mongo `chat_messages` 同步清理；看板问题文本默认脱敏（`DASHBOARD_MASK_QUESTION=true`）；停用用户日志保留用于审计，但业务界面不展示身份。
- `qa_access_logs(created_at)`、`(user_id, created_at)`、`(session_id)`。
- `import_tasks(batch_id)`、`(status)`；`outbox_events(status, next_retry_at)`。

#### 6.1.4 状态枚举与取值

| 枚举 | 取值 |
|---|---|
| 用户状态 | `active` / `disabled` |
| 知识单元状态 | `draft` / `processing` / `active` / `disabled` / `failed` / `archived` |
| 导入任务状态 | `pending` / `parsing` / `splitting` / `embedding` / `indexing` / `success` / `failed` / `cancelled` |
| FAQ 状态 | `pending_review` / `published` / `rejected` / `offline` |
| FAQ 缓存状态 | `pending` / `synced` / `failed` |
| 知识缺口状态 | `unresolved` / `resolved` / `ignored` |
| 问答结果类型 | `answered` / `faq_hit` / `permission_miss` / `gap` |
| Token 来源 | `usage`（网关返回）/ `estimate`（估算） |

状态枚举与权限码统一在 `core/contracts.py`、`core/rbac.py` 定义，禁止散落字符串。

### 6.4 Redis / MinIO

Redis：

- `faq:exact:{sha256(归一化问题)}` → `{faq_id, answer, acl_tokens, version}`
- `faq:item:{faq_id}`、`faq:cache_version`、`faq:keys:{faq_id}`
- `import:progress:{task_id}`、`lock:unit:{unit_id}`、`rate:chat:{user_id}`
- Celery broker/result；看板短缓存

MinIO（私有桶，预签名下载）：

- `raw/{yyyy}/{mm}/{uuid}/{filename}`
- `parsed/{unit_id}/{version}/content.md`
- `assets/{unit_id}/...`
- `attachments/{unit_id}/...`

### 6.5 一致性策略

- PG 为事实源；Milvus/Mongo/Redis 可重建。
- 单元编辑即发布：递增 version → 新切片 `status=0` 写入 → PG 切换 `current_version_id` → 新切片置 `status=1/is_current=true` → 删除旧版本。
- Milvus 写入 flush；查询 Strong/Session，保证导入→提问立即可见。
- 跨库写走 transactional outbox；Celery 幂等消费、指数退避、死信。
- FAQ 发布/下线通过 outbox 同步 Redis + Milvus；`cache_status` 记录真实结果。
- 每日对账：PG chunks 与 Milvus 的 unit/chunk/acl_version 差异修复。

## 7. 权限模型

### 7.1 RBAC 操作权限

权限码分 `menu` 与 `action` 两类，集中维护在 `core/rbac.py`。登录响应返回 `permissions`，前端生成动态菜单、路由守卫与按钮级指令。

内置角色矩阵：

| 权限 | system_admin | knowledge_admin | normal_user |
|---|---|---|---|
| `dashboard:read` | ✓ | ✓ | — |
| `knowledge:read/import/create/update/delete/permission` | ✓ | ✓ | — |
| `ai:access` | ✓ | ✓ | ✓ |
| `settlement:read/review/gap-manage` | ✓ | ✓ | — |
| `user:read` | ✓ | ✓ | — |
| `user:create/update/delete/reset` | ✓ | — | — |
| `role:read` | ✓ | ✓ | — |
| `role:create/update/delete/assign` | ✓ | — | — |
| `dept:read` | ✓ | ✓ | — |
| `dept:create/update/delete` | ✓ | — | — |
| `menu:org` | ✓ | — | — |
| `menu:knowledge`、`menu:settlement`、`menu:dashboard` | ✓ | ✓ | — |
| `menu:chat`、`menu:profile` | ✓ | ✓ | ✓ |

说明：`knowledge_admin` 的 `user:read/role:read/dept:read` 仅用于数据权限弹窗的只读查询，不授予 `menu:org`。管理员在 AI 数据面仍受 ACL。

### 7.2 四维数据权限

规则：`global` / `department` / `role` / `user` 四类实体，满足任意一种（OR）即可访问；默认无权限。

授权集合 SQL：

```sql
SELECT DISTINCT unit_id FROM unit_permissions
WHERE target_type = 'global'
   OR (target_type = 'department' AND target_id = :department_id)
   OR (target_type = 'role'       AND target_id = ANY(:role_ids))
   OR (target_type = 'user'       AND target_id = :user_id);
```

- 用户 token 包含：本人、角色、部门及祖先部门（`ACL_DEPT_INCLUDE_DESCENDANTS=true`）。
- 用户属于一个部门；禁用用户/角色/部门不产生 token。
- 默认无 `unit_permissions` 的单元对 AI 完全不可见。

### 7.3 两阶段召回

1. **候选召回（无 ACL）**：dense+BM25 top 20，只取 `unit_id/chunk_id/score`，不取标题/正文。
2. **权限判定**：PG 批量校验，得到 authorized / unauthorized；未授权只保留 id/score 用于计数。
3. **授权补召回**：授权候选不足（< 8）时，按 `unit_id in authorized` 再召回带正文的切片。
4. **生成**：只对授权切片 rerank、拼 Prompt、返回引用；未授权正文不进入 Prompt/响应。
5. 授权集合为空时跳过补召回，直接返回权限提示。
6. `POST /api/knowledge/check-permissions` 复用引擎；普通用户只能查自己。

`ChatOrchestrator` 直接调用 `PermissionEngine`（与 `POST /api/knowledge/check-permissions` 同一实现）；外部智能体通过该 HTTP 接口获取 `authorized_unit_ids` / `unauthorized_unit_ids`。

### 7.4 未授权提示

- 默认 `PERMISSION_NOTICE_LEVEL=count`：只返回 `unauthorized_count`，不返回标题、编号、正文、片段。
- 若验收要求点名，可切 `code_mask`（脱敏编号），仍不返回标题与正文。
- 管理员审计接口可查未授权 ID 列表；普通用户接口不返回。
- `permission_miss` 与 `gap` 分开：前者是权限问题，不进入知识缺口。

### 7.5 FAQ ACL

- 已发布 FAQ 继承关联知识单元 ACL；多关联单元取**交集**（`acl_mode=inherit_intersection`）。
- 关联单元全部写入 `faq_units`；`faqs.related_unit_id` 仅保留主关联单元用于展示与 PRD 字段兼容。
- 交集为空、存在无 ACL 的关联单元或无法推导时，必须由管理员配置 `manual` ACL 才能发布。
- 缓存命中仍实时校验 ACL；无权则跳过缓存走正常检索并提示。
- FAQ 编辑/下线/关联单元权限变更时递增缓存版本并失效旧缓存。

### 7.6 管理面与数据面

- `knowledge:update/permission` 管理员可维护全部单元（管理面）。
- AI 问答仍按 ACL 过滤（数据面），不因管理角色放行。
- 单元详情/列表对非管理员用 SQL `EXISTS` 做数据权限过滤后再分页；详情无权返回 403。

## 8. 核心流程

### 8.1 文档导入

1. 前端上传单文件/多文件/目录（`webkitdirectory`）。
2. API 校验扩展名、大小、魔数，计算 sha256；同哈希已存在时返回 `duplicate` 与既有 `unit_id`，管理员选择“新建版本/跳过”；否则存 MinIO 并创建 `import_batches` + `import_tasks`，投递 Celery。
3. Worker（LangGraph 导入图）：
   解析（PyMuPDF/python-docx/MD/TXT，可选 MinerU）→ 清洗 Markdown → 标题感知切片（500-800 字，10-15% 重叠）→ 批量远程 embedding → 写 Milvus（dense+sparse+标量）→ 写 `unit_chunks` → 更新单元状态/版本。
4. 前端轮询 `GET /api/knowledge/import/tasks/{batch_id}` 或 SSE 进度；展示每个文件结果。
5. 失败可重试；重建索引加 Redis 锁；Milvus flush + Strong 一致性。
6. `PROVIDER_MODE=mock` 时使用确定性 mock 向量与模板回答，断网可演示。

支持矩阵：

| 格式 | 支持 | 说明 |
|---|---|---|
| PDF | ✓ | 文本型直接解析；扫描件可选 OCR/MinerU（默认关闭） |
| Markdown | ✓ | 保留标题、代码块、表格 |
| Word | ✓ 仅 `.docx` | `.doc` 提示转存；python-docx 提取段落/表格 |
| TXT | ✓ | UTF-8/GBK 自动检测 |
| 目录批量 | ✓ | 保留 `relative_path`；部分成功 |

### 8.2 AI 鉴权问答

1. JWT + `ai:access`；校验会话归属。
2. FAQ 精确缓存 → 校验 FAQ ACL → 通过则流式返回，Token 计 0；无权跳过。
3. FAQ 语义匹配（`faq_vectors` cosine ≥ 0.90 + ACL）→ 同上。
4. 查询改写（可选）：最近 N 轮历史生成独立问题，失败回退原问题。
5. 候选召回（无 ACL）top 20，只取 id/score → PG 权限判定 → 授权补召回。
6. 授权切片 rerank（可选）→ Prompt：系统约束 + 授权切片 + 最近历史 + 未授权数量提示；按 token 预算截断。
7. LLM 流式 → SSE：`meta`（授权引用、未授权数量）→ `delta*` → `usage` → `done`（token、耗时、权限提示）；请求带 `stream_options.include_usage`，缺失时估算并标 `token_source`。
8. 异步写 `qa_access_logs`、Mongo `chat_messages`；FAQ 命中数原子 +1。
9. 无召回/低分 → gap；召回但全部无权限 → permission_miss。
10. 断线：前端 AbortController；后端停止 LLM 流并落部分日志。

### 8.3 FAQ 挖掘、审核与缓存

- 每日或手动扫描近 30 天 `result_type=answered` 的问答，语义聚类，频次 ≥ 阈值 → 写 `faqs(pending_review, auto_mined)`；`cluster_key` 幂等。
- 建议答案取该簇最新的授权回答；关联单元取 `authorized_unit_ids`；与所有状态已有 FAQ 去重。
- 审核可编辑答案/关联单元/ACL；通过 → published + outbox 写 Redis/Milvus，`cache_status` 记录；驳回 → rejected。
- 缓存按 `faq_cache_version` 命名空间；每个 FAQ 维护问题 hash 集合；编辑/下线/权限变更时递增版本并清理。
- 命中仍校验 ACL。

### 8.4 知识缺口

- 未召回/低分记录 gap；全部无权限记录 permission_miss，不算缺口。
- 聚类写入 `knowledge_gaps`，统计频次与最近提问时间。
- 管理端：解决、忽略、一键创建知识单元（预填标题与样例问题），单元发布后回写 resolved。

### 8.5 数据看板

- 指标：访问次数（成功回答，含 FAQ 命中）、UV（时间窗口 distinct）、知识单元数（active）、Token、平均响应时间、首 token。
- UV 不能把每日 UV 相加；总 UV 从日志去重统计。
- 排行：高频问题（聚类）、最常召回知识单元（仅授权引用）。
- 趋势：日/周访问、Token、响应时间分布；日聚合可重跑。
- 看板仅 system_admin + knowledge_admin；问题文本默认脱敏。

| `GET /api/settlement/faqs/recommendations` | — | `items[]`（id/question/recommend_count/related_unit_title/answer/status） |
| `POST /api/settlement/faqs/{id}/review` | `action`（approve / reject）、`edited_answer?` | `status`、`message` |
| `GET /api/settlement/knowledge-gaps` | `status?` | `items[]`（id/question_pattern/ask_count/last_asked_at/sample_questions/status） |

SSE 事件：

| event | data 关键字段 |
|---|---|
| `meta` | `session_id`、`faq_hit`、`citations[]`（仅授权）、`unauthorized_count`、`recalled_count`、`authorized_count` |
| `delta` | `content`（增量 Markdown） |
| `usage` | `prompt_tokens`、`completion_tokens`、`total_tokens`、`token_source` |
| `done` | `log_id`、`session_id`、`response_time_ms`、`first_token_ms`、`citations[]`、`unauthorized_count`、`faq_hit`、`permission_notice` |
| `error` | `code`、`message` |

统一错误结构：`{code, message, detail, request_id}`。SSE 的业务错误通过 `event: error` 返回，HTTP 状态仍为 200。

## 13. 测试策略

- 权限真值表：global/department/role/user 单实体、混合、默认拒绝、跨部门、多角色、禁用用户、部门祖先。
- 防泄露：未授权切片不得出现在 Prompt、SSE、日志答案、引用；提示只含数量。
- 导入：4 格式、空文件、超大文件、损坏 PDF、重复导入幂等、版本/回滚、重建索引。
- SSE：`meta → delta* → usage → done`、心跳、断开、LLM 异常降级、FAQ 命中。
- 查询：混合召回、rerank 降级、低分缺口、全部未授权。
- 集成：Testcontainers 或 compose test profile；外部模型用 mock。
- E2E：登录 → 导入 → 配权限 → 提问（成功/未授权）→ 看板 → FAQ 审核 → 缺口建档。
- 性能：首 token < 2s、检索 < 1.5s、100 并发 SSE、批量 50 文件可观测。

## 14. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 远程 embedding 限流/维度不匹配 | 导入失败/检索不可用 | 批量+重试+令牌桶；启动校验维度；换模型重建 collection |
| Milvus 中文 BM25 不可用 | 混合检索降级 | 固定镜像 + 启动探针；降级 PG 关键词 + RRF |
| 权限同步延迟 | 少量越权/漏召回 | v1 以 PG 实时判定；规模化 ACL 同步 + 二次校验 |
| 未授权提示与召回冲突 | 提示失效/缺口误报 | 两阶段召回；permission_miss 与 gap 分离 |
| FAQ 缓存越权 | 受限知识泄露 | FAQ 继承 ACL 取交集；命中实时校验；manual ACL |
| 大文件/扫描件解析慢 | 任务堆积 | 大小/页数限制、超时、异步、死信 |
| SSE 断线/代理缓冲 | 流式不可用 | 心跳、Nginx 关闭缓冲、断线重连、部分落库 |
| 模型网关不可用 | 演示中断 | Provider 抽象 + mock；超时/重试/降级 |
| Milvus 可见性延迟 | 导入后查不到 | flush + Strong/Session；验收覆盖 |
| 远程 Milvus 不可切换 | 承诺无法兑现 | 启动探针；不可用只用 Compose |
| Windows 路径/编码 | 本地跑不起来 | pathlib、UTF-8、Docker Linux 路径 |
| 密钥泄露 | 安全事故 | `.env` 不入库、日志脱敏、私有桶、密钥轮换 |
| Prompt 注入 | 越权/幻觉 | 文档视为不可信、系统提示隔离、不执行文档内指令 |
